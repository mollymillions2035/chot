# chot

Hardware DSP hotword bridge: intercepts "Hey Google" on a stock Pixel 8 and hands off to Claude Voice Mode. Pronounced "c-hot", and always written with a lowercase c, even at the start of a sentence: "chot". Class names such as `ChotAccessibilityService` follow Kotlin naming instead.

## Known issues (ultrareview, 2026-10-20)

None open. Fixed issues keep their numbers and are listed below.

### Fixed
Issues 1–5 (intercepting things the user didn't ask for), 7 and 9 were fixed on 2026-10-21. 12 and 13 were fixed later that day, then 14 and 15, then 6, and the owner had the adb shell daemon deleted, which settled 8, 10 and 11. On the Pixel 8 the fixes for 1, 2, 5, 6, 7, 9, 12, 14 and 15 held, and so did 13 as far as the test reached it. The fix for 7 removed the APK's logcat fast path, so 3 and 4 only concerned the daemon from then on, and the daemon is gone now too.

- **1. Opening the Gemini app by hand gets intercepted.** Fixed. The overlay checks now match only the overlay: Gemini's `…robin.ui.floaty.activity.FloatyActivity` (by class, or its `assistant_robin_floaty_root_container` root view), or classic Assistant's `VoiceInteractionSession` window, which accessibility reports as window type -1 (never `TYPE_SYSTEM`). The full Gemini app is `…robin.main.MainActivity` in the Google app, which the old `com.google.android.apps.search.assistant` token and `:id/assistant_` view ids also matched; both are gone, along with the bard package token and the "Gemini" title match. The older class-name tokens (`VoicePlate`, `RobinVoicePlate`, `RobinActivity`, `AssistantActivity`, `OpaActivity`, `ZeroState`, `LockscreenEntry`) are still there. Not all of them are classic-Assistant names: "Robin" is Gemini's codename. On the Pixel 8 none of them matched any Google activity seen. Anything else they might match is unverified.
- **2. Manual Google voice search gets intercepted.** Fixed. Window-state events from `NORMAL_SEARCH_CLASSES` are excluded before any overlay check. What actually caught voice search was the "Listening…" text heuristic, which content events and the mic path reached without that exclusion; it is gone, along with "Ask Gemini", which matched the Gemini app.
- **3. Other on-device sound models count as "Hey Google".** Fixed. The APK no longer reads logcat (see 7). The daemon (deleted since, see 8, 10 and 11) keyed on `I/AlwaysOnHotwordDetector: onDetected`, which only the default assistant's hotword detector logs, so generic models such as Now Playing can't produce it. Quick Phrases might, if the Google app runs them through the same detector (unverified), so the daemon treated the line as a hint and acted only once the overlay was up. The old matches were dead on Android 14+ anyway: VIMS logs under `VoiceInteractionManager` and nothing at INFO, and SoundTrigger prints `RECOGNITION (`, not `onRecognition`.
- **4. The logcat fast path presses BACK in the wrong app.** Fixed. The APK's fast path first became a hint that polled for the overlay, then was removed (see 7). The daemon (deleted since, see 8, 10 and 11), whose old patterns never matched on Android 14+ (none of them appear in the Pixel 8's log) and which this fix brought back to life, then waited for `mCurrentFocus` to be the overlay (`dumpsys window displays`) before it pressed BACK or launched Claude.
- **5. The pause switch doesn't stop the mic callback path.** Fixed. `triggerIntercept` checks `ChotPrefs.isEnabled`. The Test button (`manual = true`) still runs while paused and sends no BACK.
- **6. Locked phone drops the request.** Fixed. The trampoline called `requestDismissKeyguard(this, null)` and launched Claude right away, so Claude started behind the keyguard and never showed up after the unlock. It now asks to unlock, waits, and hands over to Claude from `onDismissSucceeded`; if the owner cancels the unlock, nothing starts. chot logs "Phone is locked: waiting for the unlock", then "Unlocked after …ms" or "Unlock cancelled: not starting Claude". `ChotTrampolineActivity.kt` `onCreate`.
  - **Seen on the Pixel 8 (2026-10-21):** "Hey Google" on the lock screen showed the unlock prompt, but after unlocking nothing happened.
  - **Checked on the Pixel 8 (`e834e29`):** 3 "Hey Google" and 1 long-press power on the lock screen all reached voice mode after the unlock, including one where the owner waited 16s to unlock. Nothing of Claude's started before the unlock, and Claude started 57–105ms after it. Cancelling the prompt started nothing and left the normal lock screen. Gemini never answered on the lock screen.
  - **PIN-only prompt:** when chot was triggered with the screen off, the unlock prompt offered only the PIN pad, without the fingerprint; with the screen already on, it offered the fingerprint. chot asked to unlock the moment the trampoline started, while the phone was still waking. It now waits until the screen has been on for 0.8s (`UNLOCK_PROMPT_SETTLE_MS`, at most 3s in all), asks right away if the screen was already on, and hands over at once if the owner unlocks from the lock screen meanwhile. The service records when the screen came on (`ACTION_SCREEN_ON`), and chot logs "Asking to unlock (screen on for …ms)".
    - **Checked on the Pixel 8 (`1c010cb`):** all 3 screen-off tries offered the fingerprint (chot asked 821–841ms after the screen came on), and a screen-on try asked at once (screen on for 2539ms). A finger on the sensor before the prompt's fingerprint icon appears doesn't register, so unlocking during the wait wasn't exercised. Whether a wait shorter than 0.8s also gets the fingerprint is untested.
    - From "Hey Google" to voice mode listening: about 0.75s unlocked, 1.8s locked with the screen on, and 2.8–4.4s from screen off, most of it the owner unlocking.
- **7. The logcat fast path never worked on Android 13+.** Fixed by removing it from the APK, along with `READ_LOGS`.
  - Since Android 13, an app reading other apps' logs needs consent for each logcat process. logd asks only while the app is the top activity; otherwise the reader silently sees only the app's own logs (`LogcatManagerService`, AOSP 14–16). `adb shell` is exempt.
  - The watcher started from `onServiceConnected`, and after a refusal its `logcatThread?.isAlive` guard kept it running blind while the checklist said it was active.
  - Making it work would have meant an Allow tap after every reboot, app update or accessibility rebind. The gain was at most one poll interval: since the fix for 4, a hint only polled for the overlay that the accessibility path already reacts to.
  - **Seen on the Pixel 8 (Android 17):** the setup script opens chot, so the consent dialog (`LogAccessDialogActivity`) did appear right after install. It was destroyed when the screen went to sleep, apparently unanswered. chot then logged no `DSP-Logcat` intercept or expired hint for the 3 hotwords said while it was on.
  - **Re-checked on the Pixel 8 (`a568a5a`):** `READ_LOGS` is gone from `dumpsys package`, no `LogAccessDialogActivity` appeared after install, and the status screen has no logcat row.
- **8, 10 and 11. The adb shell daemon's bugs.** Moot: the daemon (`scripts/pixel8-instant-adb-daemon.sh`) was deleted on 2026-10-21 at the owner's request, since the app does everything it did. It tapped blind 0.75s after every trigger at a hardcoded spot, which with a draft in the box is Send (8); it force-stopped the Google app on every trigger, which tears down the hotword detector (10); and its `ASSIST` fallback could never run because `tr -d " \r"` stripped the spaces from "No activities found" before the check (11). It also never caught long-press power, which logs no `onDetected`.
- **9. Assistant settings don't match.** Fixed by no longer changing them. When Google wasn't the default assistant, step 4 of `pixel8-adb-setup.sh` wrote `voice_interaction_service` and `assistant` itself. It set `assistant` to `OpaActivity`, where Android writes `GsaVoiceInteractionService`, and it left the ASSISTANT role alone, so a role sync could revert both. The step now only checks and warns, like chot's status screen, and the README lists Google (Gemini) as the default digital assistant as a setup requirement.
  - **Seen on the Pixel 8 (2026-10-21):** `assistant` is set to `…/com.google.android.voiceinteraction.GsaVoiceInteractionService`, the same component as `voice_interaction_service`. On `3effbab`, step 4 printed "Google is the default assistant", and `voice_interaction_service`, `assistant` and the ASSISTANT role holder were identical before and after the setup script.
  - **Owner's decision (2026-10-21):** long-pressing the power button should open a Claude voice chat, as it does now. Don't "fix" that. It works because Google is the default assistant: with `power_button_long_press=5`, the long press opens Gemini's overlay, which chot intercepts as it does for "Hey Google". A capture on `3effbab` confirmed this. 2 of 3 tries reached voice mode; for the third, see 12.
- **12. The 85ms follow-up BACK could double up.** Fixed, and later removed. `performGlobalAction(BACK)` on Pixel goes through SystemUI, so the first BACK could still be in flight at 85ms, and a BACK that arrives while no window has focus can wait for the next window to take focus, which can be Claude. The follow-up went out whenever the overlay was still listed, which it can be while closing.
  - The fix made it wait 300ms and go out only if the overlay had input focus and Claude hadn't been launched yet. It then never went out in 23 intercepts on the phone (`7553bff`, `4c1ca20`, `6f4c35b`), so it was removed: chot sends one BACK per intercept. `ChotAccessibilityService.kt` `triggerIntercept`.
  - chot logs that BACK with the window that had focus (`BACK sent (focus: …)`). The auto-tap logs when Claude's window leaves the screen before voice mode, and when it gives up after 6s.
  - **Possibly seen on the Pixel 8 (`3effbab`):** in 1 of 3 power-button tries, Claude was drawn fresh but chot logged no auto-tap, Claude flashed, and Settings came back. A second BACK landing in Claude would explain it, but the capture doesn't show BACKs, so this is unconfirmed. chot's log now would.
  - **Checked on the Pixel 8 (`7553bff`):** 12 intercepts, 5 from long-press power and 7 from "Hey Google". Every first BACK went to the overlay (`focus: com.google.android.googlequicksearchbox 'Gemini'`). The follow-up BACK never went out; the overlay was still listed at 300ms only once, after Claude had launched. Claude never flashed and closed, and the first back gesture out of Claude always landed on Settings.
- **13. Auto-tap could tap where the Voice button used to be, off screen.** Fixed. chot can find the Voice button while Claude's window is still sliding in from the right, so its bounds lie partly or wholly off the 1080-wide screen. ACTION_CLICK works there anyway, but a tap would miss, so taps now only go to bounds fully on screen (`isFullyOnScreen`, against the display's full bounds). `ChotAccessibilityService.kt` `tapVoiceButton`, `followUpVoiceButtonTap`.
  - The 380ms follow-up taps the button where it finds it then, not where it was at the first click.
  - If ACTION_CLICK fails while the button isn't fully on screen, chot doesn't tap and stays armed, so the 120ms poll retries with fresh bounds and the 1.6s coordinate fallback still applies. It logs `… is off screen and ACTION_CLICK failed: retrying` once per launch.
  - **Seen on the Pixel 8 (2026-10-21):** the settled button's left edge is at x=907–932. At tap time, chot logged a left edge of:
    - 1573 once in the first test.
    - 954, 1109 and 1137 in the re-test when Claude started a fresh `AppOnlyMainActivity` (`START … result=0`).
    - 1999, 2030 and 2030 in the re-test, and 2016 and 1827 in the power-button test, each time Claude's existing task was brought to the front instead (`result=2`). That is up to about one screen width right of the settled spot.
  - In one of the `result=2` cases ACTION_CLICK failed (`action=false, gesture=true`), the gesture tap went off screen, and Claude never entered voice mode. The "sa" the owner then found in the launcher's app search was their own earlier search for Settings, which the launcher keeps; chot didn't type it.
  - **Checked on the Pixel 8 (`7553bff`):** off-screen bounds still show up, with left edges of 1203 (twice, once with `result=0`) and 2029 (twice, `result=2`). ACTION_CLICK worked in all 11 auto-taps, so no tap went to those bounds, and the retry path wasn't exercised.
- **14. Claude stays on its last screen when that was a Claude Code session.** Fixed by the widget launch (see 15): the widget's Voice chat button starts a voice chat on top of the Code session, and Back returns to it. Without the widget set up, chot still opens Claude on its last screen, but the coordinate fallback no longer taps a labeled control such as Stop.

The launch goes `VOICE_ASSIST` → `AssistantOverlayActivity` → `AppOnlyMainActivity`, which restores the last screen.

## Claude updates
chot reads Claude's screen: labels such as "Voice Mode", where the button sits, and the activities Claude starts. A Claude update can change any of them, so some breakage is expected (owner, 2026-10-21).
- When chot isn't sure, it does nothing and logs why, rather than tapping a guess. The coordinate fallback only taps an unlabeled spot or the Voice button. The owner chose to keep it that strict, even though a renamed Voice button then needs a code change.
- The labels chot matches are lists at the end of `ChotAccessibilityService.kt`, so most breakages should be a one-line change there.
- Keep looking for sturdier ways in, and weigh them when they come up:
  - A launch from Claude that opens voice mode directly skips reading the screen entirely. The widget's Voice chat button (see 15) is one, and chot uses it first. It depends on the widget keeping a button labeled "Voice chat".
  - Recognizing the Voice button by how it looks, from `AccessibilityService.takeScreenshot` (API 30+), once an image model small and fast enough to run inside chot exists. Not planned yet.

## What the Claude app does (as of 2026-10-21)
- **Text box row:** 'Add files and more', 'Start speech input' (dictation, not voice mode), then 'Voice Mode' when the box is empty or 'Send' when it holds text. The 'Voice Mode' label sits on a non-clickable child of a 126x126 clickable View; 'Send' is a clickable Button with the same bounds. With the keyboard up, the row moves up 841px.
- **Keyboard:** a new chat focuses the box and raises the keyboard by itself, and a `VOICE_ASSIST` relaunch brings the keyboard back. BACK hides the keyboard and leaves the box focused; with no keyboard showing, BACK leaves Claude.
- **Drafts:** the new-chat screen has one draft, shared by every route to a new chat (menu, 'New session', the incognito toggle, every intent); existing chats have their own boxes. "Start voice" and the widget's Voice chat button carry the new-chat draft into the voice chat.
- **Entry points:** exported are `MainActivity` (launcher), `AssistantOverlayActivity` (`ASSIST`, `VOICE_ASSIST`) and `.deeplink.DeepLinkActivity` (https claude.ai paths and `claude:` links, none for voice). The app shortcuts "Start voice", "New session" and "Code" go to `.deeplink.AppOnlyDeepLinkActivity`, which isn't exported, with `com.anthropic.claude.intent.extra.QUICK_ACTION=START_VOICE` and `START_CHAT_MODE=BELL_MODE` for voice. No intent an outside app can send starts voice mode.
- **Widget:** `com.anthropic.claude.widget.ClaudeAppWidgetReceiver`, built with Glance, configuration optional. A fixed top row of Voice chat and Camera, then four configurable slot buttons (on the owner's: Dictation, Projects, Chats, Photos), then recent chats. Voice chat starts `AppOnlyDeepLinkActivity` (data `glance-action:/CALLBACK?appWidgetId=…`), then `AppOnlyMainActivity`. Its click extras are `WIDGET_TAP_TARGET`, `WIDGET_TAP_BUTTON` (`VOICE`, `DICTATION`, …) and `WIDGET_TAP_LAYOUT`.
- **Voice assistant service and the lock screen** (Claude 1.261019.20, checked read-only): Claude declares a full voice assistant service, `bell.assist.ClaudeVoiceInteractionService`, with its own session and recognition services, so it can be the default digital assistant, but it has no hotword. No Claude activity may show over the lock screen: nothing in the manifest or code opts in, and its config sets `supportsLaunchVoiceAssistFromKeyguard=false`. As the default assistant on a locked phone, its session shows only a non-interactive "Unlock to talk to Claude" hint, starts `AssistantOverlayActivity` behind the keyguard, and closes once the phone is unlocked or the screen goes off. So Claude itself won't run voice mode on a locked phone, and making it the default assistant gains nothing over chot's unlock-then-voice flow while turning off "Hey Google".
  - Options the owner weighed for using Claude on a locked phone (2026-10-21), none pursued: Extend Unlock with a trusted device, so the phone often isn't locked; chot's own lock-screen voice client on the Claude API, without the app's chats, memory or voice; root with an LSPosed hook that makes Claude's screens show over the lock screen, which means wiping the phone, failing Google's integrity checks (Wallet, some banking apps) and exposing the whole Claude account to anyone holding the phone. Before the first unlock after a reboot, nothing works either way.

## What the Pixel 8 does (Android 17, Google app 17.66.20)
For future matching work:
- **"Hey Google":** logs `I/SoundTriggerMiddlewareLogging: RECOGNITION (<handle>, PhraseRecognitionEventSys{… type: 0 … PhraseRecognitionExtra{id: 101 …`, then `I/AlwaysOnHotwordDetector: onDetected`, then `D/VoiceInteractionManager: Self-trigger check: VIS triggering from recent hotword`.
  - It then starts `FloatyActivity` (LAUNCH_SINGLE_TASK) within about a second. While it is up, `mCurrentFocus=Window{… u0 com.google.android.googlequicksearchbox/…robin.ui.floaty.activity.FloatyActivity}`. Most of its view ids are `assistant_robin_floaty_*`, including `assistant_robin_floaty_root_container`. Some are plain `assistant_robin_*`, and the Gemini app shares a few of those, so only the `floaty` ids identify the overlay.
- **Now Playing:** logs `FORCE_RECOGNITION (<handle>)`, then `RECOGNITION (<handle>, RecognitionEventSys{… type: 1 … data: [112, 111, 115, 95, 109, 117, 115, 105, 99, …]`. Those bytes are ASCII for `pos_music,val:…`; the text itself never appears in logcat.
- **Gemini opened by hand:** bard `BardEntryPointActivity`, then GSA `MainAssistantDeeplinkAnimated`, then `…robin.main.MainActivity`, with `assistant_robin_*` ids and no `floaty` ids.
- **Search-bar mic:** GSA `.InternalGoogleAppActivityEntrypoint`, with `googleapp_voice_search_*` ids.
- **Long-press power** (`power_button_long_press=5`): logs `D/VoiceInteractionManager: showSessionForActiveService()` and no `onDetected`, then starts the same `FloatyActivity` as "Hey Google".
- **Testing tips:**
  - `adb shell uiautomator dump` rebinds accessibility services, so chot logs "connected & armed" after each dump.
  - chot's own log (intercepts, BACKs, auto-taps; the last 100 lines) is in its prefs: `adb shell run-as dev.chot.pixel8 cat shared_prefs/chot_pixel8_prefs.xml`. `run-as` works because `build-apk.sh` builds the debug APK.
    - The file can lag: on `4c1ca20` the newest line reached disk only when chot wrote another one. Read the log on chot's screen, or force a write first (a `uiautomator dump` makes chot log "connected & armed").
  - `adb logcat -v time ActivityTaskManager:I AlwaysOnHotwordDetector:I *:S` shows each hotword, the overlay, the trampoline and Claude's activities with timestamps.
  - On the owner's machine adb isn't on PATH; use `.toolchain/android-sdk/platform-tools/adb` in the clone.
  - chot's copy of Claude's widget shows in `adb shell dumpsys appwidget` under chot's host; its id is `claude_widget_id` in chot's prefs. Binding shows the system prompt once; with "Always allow" ticked, later binds don't ask. `adb shell appwidget grantbind --package dev.chot.pixel8` should skip the prompt too (untested).
  - Leaving Claude in Recents doesn't guarantee `result=2`: backing out of Claude sometimes ends its activity, so the next launch starts it fresh. To force `result=0`, swipe Claude out of Recents.
