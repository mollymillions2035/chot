# chot

Hardware DSP hotword bridge: intercepts "Hey Google" on a stock Pixel 8 and hands off to Claude Voice Mode. Pronounced "c-hot", and always written with a lowercase c, even at the start of a sentence: "chot". Class names such as `ChotAccessibilityService` follow Kotlin naming instead.

The PR that fixes it says `Fixes #N` and adds its user-facing line, ending in `(#N)`, to `[Unreleased]` in `CHANGELOG.md`. ## Working on chot
- Work on a branch, open a PR to `main`, and merge it yourself once it's ready: the owner asked sessions to merge their own PRs. GitHub deletes a PR's branch when it merges (the repo's auto-delete setting), so only the local branch is left to remove. Commit messages start with `fix:`, `feat:`, `docs:` or `chore:`.
- The repo was rebuilt on 2026-10-23 with its history rewritten, to keep the account's former name out of the public repo; don't bring that name back. Issues and PRs #1–#69 are recreations at their original numbers, each with its original dates in a note at the top, and the commit IDs in their text point at the rewritten commits. The originals, with the original commits, are in the private `chot-private` repo.
- There's no CI and no test suite. `./scripts/build-apk.sh` has to build cleanly (it downloads a JDK, the Android SDK and Gradle into `.toolchain/` on first run, in cloud sessions too), and the phone is the real test.
- Send the owner a push notification whenever they're needed, such as at the phone.

### Cloud or local session
The main work can happen in either kind of session. What differs:
- **Cloud session:** works in a fresh clone in a container. It can build, but it can't reach the phone, and its APK is signed with the container's debug key, so it won't install over the phone's chot (uninstalling first would wipe chot's setup). It can't push tags or create releases. It tests through the local session, as below.
- **Local session:** runs on the owner's computer, in the owner's own chot clone, with the Pixel 8 on USB. It runs adb itself (`.toolchain/android-sdk/platform-tools/adb`; adb isn't on PATH there), so it builds, installs and tests directly with the owner, with nothing relayed. Its builds have the key the phone's chot and the releases use. With the owner's OK it can push tags and create releases with `gh`.
  - The clone is the owner's: run `git status` before switching branches, and stop and ask if there are local changes.
  - The computer also has a full Android Studio, installed with JetBrains Toolbox. Use it where it helps more than the command line, for example to step through chot on the phone in the debugger, profile it or run an emulator. It's a GUI, so the owner drives it. Its debug builds use the same default key (`~/.android/debug.keystore`) as `./scripts/build-apk.sh`, so they install over the phone's chot too. The script stays the standard build.
  - Keep raw test captures (`uiautomator` dumps, screenshots, logcat) in the scratchpad, never in the repo: they hold whatever was on screen.

### Testing on the phone
A local session tests directly, with the owner at the phone. A cloud session tests through the local session:
- Don't pick an existing local session on your own (owner, 2026-10-23). Ask the owner to start a new local session in their clone, or, if one already holds a lot of their work, whether it's OK to use it; then brief the one they name with `send_message`: the commit to pull, what changed, the steps, and what to report. `list_sessions` (`mine: true`) only tells you which sessions exist. The local session builds, installs with `adb install -r` (which keeps chot's setup), watches logcat and reads chot's log (see Testing tips below). While testing for a cloud session, it doesn't edit repo files.
- The local session's `send_message` back to the cloud fails, so it puts its report in its final reply, and the cloud reads that with `list_events` (kinds `result`). Reading another session's transcript takes the owner's one-time approval on a trusted device.

Rules for every round, either way: the owner does the physical steps (saying "Hey Google", unlocking, tapping); never tap Send or send anything in Claude; never speak into voice mode, and stop any voice session within a couple of seconds; don't change phone or assistant settings without asking the owner.

## Releases
`CHANGELOG.md` at the repo root follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): newest version first, an `[Unreleased]` section on top, and Added / Changed / Removed / Fixed groups. It's written for users, with GitHub issue numbers in parentheses, such as (#61). The owner's rule (2026-10-21): every release takes the `[Unreleased]` entries, which include the fixed issues, into the changelog, and the changelog goes out with the release. Versions follow semantic versioning where possible (owner, 2026-10-22): a release with only bug fixes bumps the patch number, X.Y.Z to X.Y.(Z+1).

1. Check that every issue closed since the last release has its line under `[Unreleased]` in `CHANGELOG.md`, then move those entries under a new `## [X.Y.Z] - YYYY-MM-DD` heading. Update the compare links at the end of the changelog.
2. Bump `versionName` and `versionCode` (always +1) in `app/build.gradle.kts`, in a "chore: release X.Y.Z" PR together with the changelog.
3. Build on the owner's machine. Debug builds are signed with that machine's key, and the APK has to install over the chot on the phone. Check that the certificate digest matches the previous release's APK (`apksigner verify --print-certs`) and that `adb install -r` keeps chot's setup.
4. Tag `vX.Y.Z` (annotated) on the release PR's merge commit and run `gh release create` with `chot-pixel8-X.Y.Z.apk` attached. The notes are that version's changelog section plus install and upgrade steps.

Steps 3 and 4 need the owner's machine, so a local session does them. A cloud session can't push tags or create releases in this repo; it hands those steps to a local session.

## Owner's decisions
- Long-pressing the power button should open a Claude voice chat, as it does through Gemini's overlay while Google is the default assistant (`power_button_long_press=5`). Don't "fix" that.
- Google stays the default digital assistant: its hotword detection is what makes "Hey Google" work. chot and the setup script only check and warn; they never change assistant settings.
- Voice mode has to start with or without a draft in Claude's text box, and chot must never send the draft. Clearing it was acceptable only if there was no better way; the widget launch is one.
- No path should take as long as 3s from "Hey Google" to the conversation, not counting the owner's own unlock.
- The coordinate fallback stays strict: it taps only an unlabeled spot or the Voice button, never Send, Stop, the text box or the keyboard, even though a renamed Voice button then needs a code change.
- One BACK per intercept. A second one never went out in 23 phone intercepts, and a late one can close Claude.
- No logcat reading in the app. Since Android 13 an app needs consent for each logcat process, asked only while it's the top activity, so it would need an Allow tap after every reboot, update or accessibility rebind (`adb shell` is exempt). The adb shell daemon that used logcat was deleted; don't bring it back.
- On a locked phone chot waits for the unlock and starts Claude after it; a cancelled unlock starts nothing.
- chot never holds `WRITE_SECURE_SETTINGS` (owner, 2026-10-23, #64). Turning an accessibility service on by hand in Settings is the normal behaviour for any app; when the service was on and a force-stop turned it off, chot notifies instead. The notification permission is asked for on chot's screen, since the owner may install with plain `adb install`.
- chot is dedicated to the public domain under CC0 1.0 (`LICENSE`; owner, 2026-10-23), since who owns AI-written code is unsettled. CC0 waives every right where the law allows and falls back to a fully permissive license where it doesn't.

## How chot works (1.2.0)
- **Intercept** (`ChotAccessibilityService`): matches only Gemini's `…robin.ui.floaty.activity.FloatyActivity` (by class, or its `assistant_robin_floaty_root_container` root view) or classic Assistant's `VoiceInteractionSession` window, which accessibility reports as window type -1, unless it holds the Quick Phrases pill (`quick_phrases_base_container`). Window-state events from `NORMAL_SEARCH_CLASSES` are skipped first, and there are no text or generic view-id matches, so the Gemini app, the search-bar mic and Now Playing are left alone. The service config's `packageNames` limits events to Google, Gemini and Claude (#57); the mic-recording callback still checks for the overlay on its own. The intercept cooldown is a 2500ms constant in the service. The older class tokens (`VoicePlate`, `RobinVoicePlate`, `RobinActivity`, `AssistantActivity`, `OpaActivity`, `ZeroState`, `LockscreenEntry`) are still there; none matched anything on the Pixel 8. `triggerIntercept` checks the pause switch and sends one BACK, logged with the window that had focus. The Test button runs while paused and sends no BACK.
- **Trampoline** (`ChotTrampolineActivity`): on a locked phone it asks to unlock once the screen has been on for 0.8s, or right away if it already was, and continues from `onDismissSucceeded`; if the phone is still locked 30s after the hotword, it gives up and starts nothing (#52). Its window doesn't keep the screen on. Then it takes audio focus, waits up to 340ms for Gemini to free the mic, and presses the widget's Voice chat button.
- **Widget launch** (`ClaudeWidget`): chot's own never-shown copy of Claude's widget, bound once from "4. Claude Widget" on chot's screen with a one-time system prompt. The trampoline lays it out while waiting for the mic and clicks the button labeled "Voice chat", which fires Claude's own PendingIntent; Android allows it as `BAL_ALLOW_VISIBLE_WINDOW` for the trampoline. After the press chot waits 1s for Claude's window, else launches Claude the old way, and 0.7s after the window for voice mode, else looks for the Voice button. Every press logs a harmless `W/RemoteViews: getLaunchOptions: view.getDisplay() is null!`. If the copy has no Voice chat button, which happens after Claude is force-stopped, chot asks Claude to redraw it (see #51) and takes the old path that once.
- **Old path** (no widget set up, or the widget press failed): a `VOICE_ASSIST` launch plus the auto-tap. The auto-tap finds the Voice button by label and taps only bounds fully on screen: Claude's window can still be sliding in, with the button up to a screen width right of its settled spot (x=907–932). A 380ms follow-up taps the button where it is then, and the 1.6s coordinate fallback is restricted as above. The "Auto-tap" checkbox gates only the taps (Voice button search, follow-up tap, node dump, coordinate fallback), never the launch of Claude when the widget press fails (#53). The 1200ms node dump logs text only for clickable nodes or nodes with a view id, and the length of any other text (#58). Every timer uses `SystemClock.elapsedRealtime()`, not the wall clock (#54).
- **Force-stop notice** (#61, #64): a force-stop turns chot's accessibility service off (see Force-stop below), and chot can't turn it back on: it no longer holds `WRITE_SECURE_SETTINGS`. `accessibility_service_wanted` in chot's prefs is set in `onServiceConnected` and cleared in `onUnbind`, which runs when the service is turned off in Settings but not on a force-stop. On opening chot, `MainActivity.onResume` finds the service wanted but off, asks for the notification permission if it's missing, and posts the `ChotNotifications` "service is off" notification, which opens Accessibility settings; `onServiceConnected` cancels it. "1. Enable Accessibility" always opens Accessibility settings. Nothing can run before chot is opened: a force-stopped app gets no broadcasts until it's launched, so the first sign of a force-stop is still "Hey Google" opening Gemini.
- **Timing on the Pixel 8:** from "Hey Google" to voice mode listening, about 0.75s unlocked, 1.8s locked with the screen on, and 2.8–4.4s from screen off, mostly the owner unlocking. The widget lays out in 20–80ms; Claude's window and voice mode show 180–290ms after the press when warm, and voice mode 505ms after it when cold.

## Claude updates
chot reads Claude's screen: labels such as "Voice Mode", where the button sits, and the activities Claude starts. A Claude update can change any of them, so some breakage is expected (owner, 2026-10-21).
- When chot isn't sure, it does nothing and logs why, rather than tapping a guess. The coordinate fallback only taps an unlabeled spot or the Voice button. The owner chose to keep it that strict, even though a renamed Voice button then needs a code change.
- The labels chot matches are lists at the end of `ChotAccessibilityService.kt`, so most breakages should be a one-line change there.
- Keep looking for sturdier ways in, and weigh them when they come up:
  - A launch from Claude that opens voice mode directly skips reading the screen entirely. The widget's Voice chat button (see How chot works) is one, and chot uses it first. It depends on the widget keeping a button labeled "Voice chat".
  - Recognizing the Voice button by how it looks, from `AccessibilityService.takeScreenshot` (API 30+), once an image model small and fast enough to run inside chot exists. Not planned yet.

## What the Claude app does (as of 2026-10-21)
- **Text box row:** 'Add files and more', 'Start speech input' (dictation, not voice mode), then 'Voice Mode' when the box is empty or 'Send' when it holds text. The 'Voice Mode' label sits on a non-clickable child of a 126x126 clickable View; 'Send' is a clickable Button with the same bounds. With the keyboard up, the row moves up 841px.
- **Last screen:** a `VOICE_ASSIST` launch goes `AssistantOverlayActivity` → `AppOnlyMainActivity`, which restores Claude's last screen, including a Claude Code session, which has no Voice button. The widget's Voice chat button starts a voice chat on top of whatever is there; Back returns to it.
- **Keyboard:** a new chat focuses the box and raises the keyboard by itself, and a `VOICE_ASSIST` relaunch brings the keyboard back. BACK hides the keyboard and leaves the box focused; with no keyboard showing, BACK leaves Claude.
- **Drafts:** the new-chat screen has one draft, shared by every route to a new chat (menu, 'New session', the incognito toggle, every intent); existing chats have their own boxes. "Start voice" and the widget's Voice chat button carry the new-chat draft into the voice chat.
- **Entry points:** exported are `MainActivity` (launcher), `AssistantOverlayActivity` (`ASSIST`, `VOICE_ASSIST`) and `.deeplink.DeepLinkActivity` (https claude.ai paths and `claude:` links, none for voice). The app shortcuts "Start voice", "New session" and "Code" go to `.deeplink.AppOnlyDeepLinkActivity`, which isn't exported, with `com.anthropic.claude.intent.extra.QUICK_ACTION=START_VOICE` and `START_CHAT_MODE=BELL_MODE` for voice. No intent an outside app can send starts voice mode.
- **Widget:** `com.anthropic.claude.widget.ClaudeAppWidgetReceiver`, built with Glance, configuration optional. A fixed top row of Voice chat and Camera, then four configurable slot buttons (on the owner's: Dictation, Projects, Chats, Code), then recent chats. Voice chat starts `AppOnlyDeepLinkActivity` (data `glance-action:/CALLBACK?appWidgetId=…`), then `AppOnlyMainActivity`. Its click extras are `WIDGET_TAP_TARGET`, `WIDGET_TAP_BUTTON` (`VOICE`, `DICTATION`, …) and `WIDGET_TAP_LAYOUT`.
- **Voice assistant service and the lock screen** (Claude 1.261019.20, checked read-only): Claude declares a full voice assistant service, `bell.assist.ClaudeVoiceInteractionService`, with its own session and recognition services, so it can be the default digital assistant, but it has no hotword. No Claude activity may show over the lock screen: nothing in the manifest or code opts in, and its config sets `supportsLaunchVoiceAssistFromKeyguard=false`. As the default assistant on a locked phone, its session shows only a non-interactive "Unlock to talk to Claude" hint, starts `AssistantOverlayActivity` behind the keyguard, and closes once the phone is unlocked or the screen goes off. So Claude itself won't run voice mode on a locked phone, and making it the default assistant gains nothing over chot's unlock-then-voice flow while turning off "Hey Google".
  - Options the owner weighed for using Claude on a locked phone (2026-10-21), none pursued: Extend Unlock with a trusted device, so the phone often isn't locked; chot's own lock-screen voice client on the Claude API, without the app's chats, memory or voice; root with an LSPosed hook that makes Claude's screens show over the lock screen, which means wiping the phone, failing Google's integrity checks (Wallet, some banking apps) and exposing the whole Claude account to anyone holding the phone. Before the first unlock after a reboot, nothing works either way.

## What the Pixel 8 does (Android 17, Google app 17.66.20)
For future matching work:
- **"Hey Google":** logs `I/SoundTriggerMiddlewareLogging: RECOGNITION (<handle>, PhraseRecognitionEventSys{… type: 0 … PhraseRecognitionExtra{id: 101 …`, then `I/AlwaysOnHotwordDetector: onDetected`, then `D/VoiceInteractionManager: Self-trigger check: VIS triggering from recent hotword`.
  - It then starts `FloatyActivity` (LAUNCH_SINGLE_TASK) within about a second. While it is up, `mCurrentFocus=Window{… u0 com.google.android.googlequicksearchbox/…robin.ui.floaty.activity.FloatyActivity}`. Most of its view ids are `assistant_robin_floaty_*`, including `assistant_robin_floaty_root_container`. Some are plain `assistant_robin_*`, and the Gemini app shares a few of those, so only the `floaty` ids identify the overlay.
- **Now Playing:** logs `FORCE_RECOGNITION (<handle>)`, then `RECOGNITION (<handle>, RecognitionEventSys{… type: 1 … data: [112, 111, 115, 95, 109, 117, 115, 105, 99, …]`. Those bytes are ASCII for `pos_music,val:…`; the text itself never appears in logcat.
- **Gemini opened by hand:** bard `BardEntryPointActivity`, then GSA `MainAssistantDeeplinkAnimated`, then `…robin.main.MainActivity`, with `assistant_robin_*` ids and no `floaty` ids.
- **Search-bar mic:** GSA `.InternalGoogleAppActivityEntrypoint`, with `googleapp_voice_search_*` ids.
- **Quick Phrases** (a ringing timer, and likely alarms and calls): the Google app logs `#QP Start QuickPhrases` and `D/VoiceInteractionManager: Self-trigger check: VIS self trigger not allowed.`, but no `onDetected` and no `FloatyActivity`. Its `VoiceInteractionSession` window turns visible with a small pill at the top (about [378,141][701,280]) and stays up until the timer stops. In that window are `quick_phrases_base_container`, `quick_phrases_pill_container` (described as 'Say “Stop”. Double tap on the pill for more information.') and `quick_phrases_pill_phrase` ('Stop'). Saying "Stop" logs `#QP Received Quick Phrase invocation`, then a `clock-app://` start of deskclock's `HandleUris`. The window has no focus, so focus stays on the Clock app or the lock screen. With Gemini, "Hey Google" never made that window visible; it showed only `FloatyActivity`.
- **Long-press power** (`power_button_long_press=5`): logs `D/VoiceInteractionManager: showSessionForActiveService()` and no `onDetected`, then starts the same `FloatyActivity` as "Hey Google".
- **Hotword log lines:** only the default assistant's detector logs `onDetected`, so generic sound models such as Now Playing can't produce it; Quick Phrases don't (see above). VIMS logs under `VoiceInteractionManager`, nothing at INFO, and SoundTrigger prints `RECOGNITION (`, not `onRecognition`.
- **Assistant settings:** with Google as the default assistant, `voice_interaction_service` and `assistant` are both `…/com.google.android.voiceinteraction.GsaVoiceInteractionService`, and the ASSISTANT role holder is `com.google.android.googlequicksearchbox`. Changing the assistant in Settings updates all three together; writing them over adb doesn't touch the role.
- **BACK:** `performGlobalAction(BACK)` goes through SystemUI and reaches whichever window has input focus when it arrives. If no window has focus yet (an activity is still starting), it waits for the next one, which can be Claude.
- **Force-stop:** force-stopping chot (`am force-stop` or Settings' Force stop) removes it from `enabled_accessibility_services` (the setting goes to `null` if it was the only one) and unbinds it, without calling `onUnbind`. The Accessibility settings screen then shows chot off. The setting clears a moment later: once in five force-stops it still held chot when read right after `am force-stop`, and was `null` a second on. Installing a build that doesn't request a permission makes Android drop its grant for good (seen with `WRITE_SECURE_SETTINGS`, #64).
- **Unlock prompt:** asked for with `requestDismissKeyguard` while the phone is still waking from screen-off, it offers only the PIN pad; once the screen has been on for about 0.8s, it offers the fingerprint. A finger on the under-display sensor before the prompt's fingerprint icon appears doesn't register.
- **Testing tips:**
  - `adb shell uiautomator dump` rebinds accessibility services, so chot logs "connected & armed" after each dump.
  - chot's own log (intercepts, BACKs, auto-taps; the last 100 lines) is in its prefs: `adb shell run-as dev.chot.pixel8 cat shared_prefs/chot_pixel8_prefs.xml`. `run-as` works because `build-apk.sh` builds the debug APK.
    - The file can lag: on `11025fd` the newest line reached disk only when chot wrote another one. Read the log on chot's screen, or force a write first (a `uiautomator dump` makes chot log "connected & armed").
  - `adb logcat -v time ActivityTaskManager:I AlwaysOnHotwordDetector:I *:S` shows each hotword, the overlay, the trampoline and Claude's activities with timestamps.
  - On the owner's machine adb isn't on PATH; use `.toolchain/android-sdk/platform-tools/adb` in the clone.
  - chot's copy of Claude's widget shows in `adb shell dumpsys appwidget` under chot's host; its id is `claude_widget_id` in chot's prefs. Binding shows the system prompt once; with "Always allow" ticked, later binds don't ask. `adb shell appwidget grantbind --package dev.chot.pixel8` should skip the prompt too (untested).
  - Force-stopping Claude leaves chot's widget copy stale until the next intercept redraws it (see #51), so the press after a force-stop takes the old path. End test voice chats in the app rather than with `am force-stop`.
  - Leaving Claude in Recents doesn't guarantee `result=2`: backing out of Claude sometimes ends its activity, so the next launch starts it fresh. To force `result=0`, swipe Claude out of Recents.
